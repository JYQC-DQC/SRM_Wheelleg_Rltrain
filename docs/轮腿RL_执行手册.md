## 0. 怎么用这份手册

### 0.1 三个角色
| 角色 | 负责什么 |
|---|---|
| **你** | 硬件操作（电机配置、标定、辨识、上车）、在云端点按钮训练、看曲线、决定是否进入下一步 |
| **Codex（写代码的 AI）** | 按第 4 节的工作包（WP）一个一个写代码和测试 |
| **我（评审）** | 每个检查点（R0、R1……）帮你检查代码、数据和训练结果，判断能不能进入下一步 |

### 0.2 基本规则
1. **按编号顺序做。** 前一步的"完成标准"没达到，不进入下一步。**整体节奏按第 8 节执行（辨识不省略，各条线并行推进）。**
2. **每完成一个检查点（R 开头），就把第 6 节列出的材料发给我。** 我确认后再继续。
3. **任何会让机器人动起来的操作，都先做好安全措施**（§3.0）。
4. **所有参数只维护一份**（`config/` 下的 yaml），不要在多处手抄。
5. **不懂的词先查第 1 节和第 7 节。**

## 1. 强化学习 15 分钟入门（只讲本项目用得到的）

### 1.1 几个最基本的词
| 词 | 意思 | 在本项目里是什么 |
|---|---|---|
| 环境（env） | 仿真出来的世界，加上机器人 | Isaac Lab 里同时运行的 4096 台虚拟机器人 |
| 观测（obs） | 机器人每一步能"看到"的数字 | 35 个数：角速度、重力方向、关节角、关节速度、上一步动作、指令…… |
| 动作（action） | 机器人每一步输出的数字 | 6 个数：4 个髋电机的目标角度、2 个轮子的目标转速 |
| 策略（policy / actor） | 从观测算出动作的神经网络 | 一个 35 → 256 → 128 → 64 → 6 的 MLP，最后部署到 H7 上的就是它 |
| 奖励（reward） | 每一步给机器人打的分 | 速度跟得准就加分，摔倒、抖动就扣分 |
| 回合（episode） | 从重置到摔倒或超时的一段过程 | 一般最长 20 s |
| Critic（价值网络） | 训练时用来估计"现在这个状态以后能得多少分"的网络 | 只在训练时使用，**不上 H7** |
| PPO | 一种训练算法：让机器人试，得分高的动作多做，得分低的少做 | 华南虎、星云用的都是它 |
| 迭代（iteration） | PPO 的一轮：所有环境各跑 48 步，然后更新一次网络 | 一次训练通常跑几千到两万轮 |
| checkpoint（`model_xxxx.pt`） | 训练过程中保存下来的网络参数 | 可以从它继续训练（续训），也可以从它导出 ONNX |
| ONNX | 一种通用的网络文件格式 | 导出后交给 X-CUBE-AI，生成 H7 上运行的 C 代码 |
| 域随机化（DR） | 训练时随机改变摩擦、质量、延迟等参数 | 让策略在真车上也能用（真车和仿真总有差别） |
| sim2sim | 把策略放到另一个仿真器（MuJoCo）里测试 | 上真车前的最后一道检查 |
| sim2real | 从仿真迁移到真车 | 最终目标 |

### 1.2 一次训练实际在做什么
```
重复 N 轮（例如 5000 轮）：
  1. 4096 台虚拟机器人用当前的策略各跑 48 步（0.48 s），记录观测、动作、奖励
  2. Critic 估计每一步"以后还能得多少分"
  3. PPO 用这些数据更新策略：比预期得分高的动作，让它更容易被选中
  4. 每隔一段时间保存一次 checkpoint
```

### 1.3 训练曲线怎么看（TensorBoard）
| 曲线 | 正常情况 | 不正常时说明什么 |
|---|---|---|
| `Train/mean_reward`（平均总奖励） | 先快速上升，然后变平 | 一直不涨：奖励设计有问题或任务太难；突然掉下来：训练崩了，回到上一个 checkpoint |
| `Train/mean_episode_length`（平均回合长度） | 逐渐涨到最大值（例如 20 s 对应 2000 步） | 一直很短：机器人一开始就摔，先查模型和终止条件 |
| `Episode_Reward/xxx`（每一项奖励） | 跟踪类的项上升，惩罚类的项接近 0 | 某一项惩罚特别大：这一项在主导训练，降低它的权重 |
| `Loss/value_function` | 先上升，后下降并趋于平稳 | 一直很大：奖励尺度太大，或者 Critic 拿到的信息不够 |
| `Policy/mean_noise_std`（动作噪声） | 慢慢下降 | 降得太快：探索不够；不降：没学到东西 |
| `Loss/learning_rate`、KL | 自适应学习率在 1e-5 到 1e-3 之间波动 | 学习率掉到很低并且一直不回升：更新步子太大，训练在震荡 |

曲线的具体名称以 rsl_rl 的版本为准 [核]。**不要只看总奖励**，每一项奖励都要看。

### 1.4 新手最常见的三个误区
1. **奖励涨了就以为成功了。** 一定要用 play 看视频，再跑固定评测集（指南 §5.12）。策略常常会钻奖励设计的空子。
2. **一次改很多东西。** 每次只改一处，否则不知道是哪一处起了作用。
3. **仿真里行就直接上车。** 必须先过 sim2sim（MuJoCo），再架空测试，然后才能落地。

## 3. 硬件操作详细步骤

### 3.0 安全规则（每次通电前都检查一遍）
1. **急停：** 电机电源回路里串一个急停开关（或者固态继电器加遥控断电）。急停能切断电机电源，但不能切断主控。
2. **限流：** 第一次给电机上电时用可调电源，电压 24 V，限流 3–5 A；确认没问题后再接电池。
3. **固定：** 单个电机调试时要固定在台钳或桌面上；整车测试时先吊起来，让轮子离地。
4. **写参数前先失能。** DMTool 里点"写参数"后芯片会自动复位，必须在电机失能（红灯）时操作 [DMTool 说明书第 17 页]。
5. **离开时断电。** 电机使能（绿灯）时人不要离开。

### 3.1 配置 4 个 8009P（DMTool，每个电机单独做，约 1 小时）
1. **连线：** 只接一个电机。电机电源接 24 V；电机的调试串口（GH1.25 三针：GND RX TX）接 USB2FDCAN 模块或 USB 转串口 [8009P 手册第 6 页]。
2. 打开 DMTool → 选择串口 → 打开串口 → **"读参数"**。核对：极对数 21、减速比 9。**这两个参数不要改** [DMTool 第 17 页]。
3. **先导出一份原始参数作为备份**（参数预设 → 导出，txt 格式），存为 `config/hw/dm8009p_<位置>_factory.txt`。
4. 修改以下参数：

| 参数 | 设定值 | 理由 |
|---|---|---|
| CAN_ID | 左前 0x01、左后 0x02、右前 0x03、右后 0x04 | 说明书建议小于 16，避免和错误码冲突 |
| Master ID | 0x11、0x12、0x13、0x14（各不相同） | 反馈帧的 ID，用来区分是哪个电机回的 |
| CAN 波特率 | 1 Mbps | 默认值；装机前设好，不要装机后再用 CAN 去改 [8009P 手册第 9 页] |
| 控制模式 | MIT | 固件只发力矩（kp = kd = 0） |
| PMAX / VMAX | **12.5 / 45**（VMAX 默认是 30） | 队内 DM 驱动把 J8009P 的 PMAX 12.5、VMAX 45 写成了宏（`dmmotor.h:26-31`），电机里的设置必须和它一样，否则换算会按比例错掉 |
| **TMAX** | **54**（默认是 10！） | 同样是队内驱动里的宏（星云也用 54）。12 位编码下分辨率约 0.026 Nm。实际输出仍由固件限幅在 ±40 Nm |
| 欠压 | 16–18 V [判]（DMTool 默认 20 V，手册要求不低于 15 V） | 6S 电池满电 25.2 V，起跳时会瞬间压降；要和超电方案一起实测确定 |
| 过压 | 30 V | 6S 满电 25.2 V，再留一点余量 |
| 过温 | 100 °C | 说明书建议值 |
| 过流 | 0.95 | 说明书建议不超过 0.98 |
| CAN Timeout | 2000（单位 50 µs，即 100 ms） | H7 死机或断线 100 ms 后，电机自动失能 |

5. 点 **"写参数"**，等电机自动复位后再 **"读参数"**，逐项核对。然后导出为 `config/hw/dm8009p_<位置>_final.txt`。
6. **检查固件版本**（读版本）。4 个电机的固件最好是同一个版本，版本号记进 `config/hw/README.md`。V3 和 V4 驱动在串口能读的参数上有差别 [DMTool 第 15 页]。
7. 编码器校准**不要做**：出厂已经校准过，只有更换驱动板或出现异常振动时才需要 [DMTool 第 24–26 页]。

### 3.2 配置 2 个 C620（约 15 分钟）
1. 每个 C620 单独上电。**短按 1 次 SET**（指示灯熄灭）→ 再短按 N 次（N 就是 ID）→ 3 秒不操作就会自动保存 → 重新上电。左轮设为 ID 1，右轮设为 ID 2 [C620 手册"SET 按键操作"]。
2. **电机校准：** 在轮子还没装上（空载）时，长按 SET 直到绿灯快闪再松开，等它自动转完。更换电机、电调或减速箱后都要重做。
3. 两个 C620 接在同一条 CAN 上时，ID 不能重复，否则会报警并关闭输出。

### 3.3 接线
- **CAN1：** 左腿 2 个 8009P（CAN ID 0x01、0x02）+ 左轮 C620（ID 1）。**CAN2：** 右腿 2 个 8009P（0x03、0x04）+ 右轮 C620（ID 2）。**CAN3：** 超级电容、裁判系统、双板通信等。
  - 两个 C620 不在同一路总线上，所以 ID 不会冲突；仍然分别设成 1 和 2，日志里更容易区分。
- 每条总线两端各接一个 120 Ω 终端电阻。断电后用万用表量 CANH 和 CANL 之间的电阻，应该约 60 Ω。
- 达妙板供电 12–24 V（支持 6S）。CAN 收发器由 5 V 供电，只用 USB 供电时也能工作 [DM-MC-Board02 手册第 4 页]。

### 3.4 第一次"解禁"（使能）电机
**先在 DMTool 里，一次只接一个电机：**
1. 电机固定好，输出轴不接负载。DMTool 切到 CAN 模式，输入 CAN ID，确认能匹配到 Master ID [DMTool 第 28 页]。
2. 调试页 → MIT → 点 **"使能"**（绿灯亮）。
3. **阻尼测试：** 速度 0、KD = 1，其余都是 0，勾选"定时发送"。用手转输出轴，应该感到均匀的阻力。
4. **位置测试：** 先点"保存零点"，把当前位置设为零点，然后给位置 0.5 rad、KP = 10、KD = 1，看电机能不能平稳转过去。说明书示例用的是 KP 25 / KD 2.5；第一次用小一点的值。**位置控制时 KD 不能为 0**，否则会振荡 [8009P 手册第 7 页]。
5. **力矩测试：** KP = 0、KD = 0，只给力矩 1 Nm，电机应该朝一个方向缓慢加速。记下这个方向。
6. 先点"停止"，再点"失能"（红灯）[DMTool 第 31 页]。
   - 注意：第 4 步的"保存零点"只是为了测试。真正的零点在 §3.5 里重新标定。

**然后用 H7 固件（FW0/FW1 完成后）：**
1. 上电顺序：先给主控上电 → 再合上电机电源 → 等 1 s 让电机完成自检 → 读一帧反馈，确认没有错误码。
2. 有错误码时先发"清除错误"，再发"使能"。
   - 达妙电机的特殊命令是 8 字节帧：前 7 个字节为 0xFF，最后一个字节表示命令（使能 FC、失能 FD、保存零点 FE、清除错误 FB）。队内驱动 `Modules/motor/DMmotor/dmmotor.c` L28-32 已经按这个格式定义；目前只封装了使能和设零位，失能和清错由 FW1 补上。
3. 使能后立刻以 500 Hz 连续发送**零力矩**的 MIT 帧。只要中断超过 100 ms，电机就会因为通讯超时自动失能（§3.1 设置的 CAN Timeout）。
4. 失能顺序：先把力矩斜坡降到 0，再发"失能"。

### 3.5 标定零点和方向（最容易出错的一步，必须仔细做）
**先分清三个"姿态"，它们不是同一个东西：**
| 名称 | 是什么 | 由谁决定 | 用在哪里 |
|---|---|---|---|
| **模型零位**（URDF 零位、策略零位） | URDF/USD 里所有关节角都等于 0 时机器人的样子 | 由导出 URDF 时每个关节坐标系的摆放方式决定；在 Isaac 里把关节角全设为 0 就能看到这个姿态 | 仿真和策略里所有关节角都以它为 0 |
| **标定参考姿态**（机械零位） | 一个在实车上能**准确、重复摆出来**的姿态，例如两条腿卡进夹具，或者靠在机械限位上 | 你自己选，选好后要能复现 | 只用来在实车上"保存零点"。电机读数在这个姿态下等于 0 |
| **默认姿态**（`q_default`，站立姿态） | 机器人正常站立时的关节角（相对模型零位） | 训练配置里设定 | 动作 `q_ref = q_default + 0.5·a`；观测里放的是 `q − q_default` |

**它们之间的关系：** `模型关节角 = sign × 电机读数 + offset`。其中 offset 是"标定参考姿态"在模型里的关节角，从 SolidWorks 里量出来，写进 `zero_offsets.yaml`；sign 是 ±1，表示方向是否相反。
- 例子：两条腿靠在后方的机械限位上时，在 SolidWorks 里量得前大腿关节相对模型零位是 +0.26 rad。那么在这个姿态下给电机"保存零点"后，电机读数是 0，换算出的模型关节角就是 0 + 0.26 = 0.26 rad。星云实际用的就是这种做法，偏置约为 ±0.2569 rad 和 ±0.767 rad [码 FD-deploy]。
- 模型零位往往是一个实车摆不出来的姿态（比如腿伸直），所以才需要单独选一个标定参考姿态。

**操作步骤：**
1. **选一个机械上能准确复现的参考姿态。** 推荐做一个 3D 打印的夹具，把两条腿卡在固定位置；或者让两条腿靠在机械限位上（星云用的是导轮着地、两腿向后的姿态 [码 FD-deploy]）。
2. **在参考姿态下给每个电机"保存零点"**（DMTool 或固件命令）。8009P 的输出轴是单圈绝对编码器，零点掉电后不丢 [8009P 手册第 4 页]。
3. **在 SolidWorks 里量出参考姿态和"策略零位"之间每个关节的角度差**，写进 `config/hw/zero_offsets.yaml`。策略零位就是 URDF 里所有关节角为 0 的姿态。
4. **检查工作范围不跨越 ±π。** 上电后的位置读数限定在 [−π, π]；如果关节的工作范围跨过 ±π，读数会跳变。万一跨过了，就换一个参考姿态重新标定。
5. **方向检查：** 每个电机正向转一点，看 URDF 里对应的关节是不是也正向转。不一致的，在 `config/hw/joint_map.yaml` 里把这个关节的 `sign` 设为 −1。
6. **检验：** 再做 3 个不同的夹具姿态（或者用量角器量），比较读数换算出来的关节角和 CAD 值，误差 < 0.5°。
7. 以后每次拆装腿、更换电机，都要重做第 2–6 步。

### 3.6 IMU（板载 BMI088）
1. 确定 IMU 芯片坐标轴和机身坐标轴（x 朝前、z 朝上）之间的关系，写进 `config/hw/imu.yaml`。
2. **陀螺零偏：** 机身静止 30 s，取平均值作为零偏。每次上电都自动做一次（上电后静止 2 s）。
3. **姿态解算：** 用 Mahony 或 EKF 得到四元数，算出 `重力投影 = Rᵀ·[0,0,−1]`。
4. **检验：**
   - 机身水平放置时，重力投影应约为 (0, 0, −1)；
   - 机头抬高（pitch 抬头），重力投影的 x 分量应该是正还是负，要和 Isaac Lab 里同样姿态的值对比确认；
   - 左右倾斜同样检查。
   - 这一步错了，策略上车就会立刻倒，是最常见的问题之一。

### 3.7 称重和质心
1. 分别称整车、单条腿（拆下）、轮子、云台的重量。
2. 测质心高度：把车放在两个支点上倾斜，或者吊起来找平衡点。也可以直接用 SolidWorks 的质量属性，再和称重结果对比。
3. 整车质量和 CAD 的差应在 2–3 kg 以内，越小越好（星云经验）。差得多时，先把电池、线束等补进 CAD。

### 3.8 髋电机力矩读数标定（约半天）
- **目的：** 8009P 反馈的力矩是由电流估算出来的，可能有几个百分点到 10% 的误差。后面辨识气弹簧时要用这个读数，所以先标定。
- **步骤：**
  1. 拆掉气弹簧，把车架空并固定机身。
  2. 在轮轴上挂一个已知重量（例如 5 kg 哑铃，绳子要竖直）。
  3. 用位置 PD 把腿停在 4 个不同姿态，每个姿态静止 3 s，记录两个电机的力矩，取平均值。
  4. 用 WP1 的五连杆雅可比，算出这个重物在每个电机上产生的理论力矩：`τ = Jᵀ·[0, −m·g]`。另外再减去不挂重物时测出的力矩（腿自身的重力）。
  5. 对每个电机，拟合"实测 / 理论"的比例，得到力矩缩放系数，写进 `config/hw/torque_scale.yaml`。
- **完成标准：** 每个电机在 4 个姿态下的比例差异 < 5%。差异更大的话，检查几何参数和绳子是否竖直。

### 3.9 髋电机 real2sim 扫频（约 1 天，需要 FW3）
1. 装回气弹簧（也可以先不装弹簧做一遍，更容易对上）。车架空、机身固定、轮子离地。
2. 固件辨识模式按预设轨迹运行：
   - 两条腿同相、反相各做一遍正弦扫频：频率 0.5 → 5 Hz，幅度从小到大；
   - 再做几组阶跃。
   - 记录：时间戳、指令、4 个关节角和速度、力矩反馈、温度，频率 500 Hz。
3. 数据存为 `data/ident/hip_sweep_<日期>.csv`。
4. 用仓库 A 的辨识脚本（WP-ID）把同样的指令放进 MuJoCo 回放，并自动搜索 armature、关节摩擦、阻尼、力矩缩放和延迟，使曲线误差最小。
5. **完成标准：** 关节角曲线基本重合；高频段的相位差可以解释为延迟。
- 这是华南虎推荐的方法：必须带着整条腿做，因为大部分 gap 来自并联耦合。

### 3.10 轮电机（约半天）
1. **空载：** 轮子离地，给速度阶跃（10 / 30 / 60 rad/s），记录响应，得到摩擦、阻尼和速度环响应。实测最高转速，用来验证 15.76:1 时约 61.5 rad/s 的估算。
2. **扭矩：** 把轮子卡住（夹具或制动），C620 给 5、10、15、20 A 的电流，用拉力计或杠杆加秤测出轮端扭矩，验证约 4.9 Nm@20 A 的估算。
   - 没有测力工具的话，用整车推测：在平地上让车加速，用测出的加速度和整车质量反推扭矩（误差较大，但够用）。
3. 结果写进 `config/robot.yaml` 的轮子部分。

### 3.11 气弹簧（约 1 天）
按指南 §4 第 5 条做：**先拆弹簧扫一遍网格，再装弹簧扫一遍，两次相减**，解出 F(L)。
- **网格：** 每条腿在两个电机的工作范围内取约 10×10 个姿态，每个姿态停 1–2 s。每个姿态从两个方向各到达一次。
- 数据存为 `data/ident/spring_with_<日期>.csv` 和 `spring_without_<日期>.csv`。
- 分析脚本由仓库 A 的 WP-ID 提供，输出 `F0`、`k`、`c`、两个方向的滞回量和拟合残差图。
- 拟合结果写进 `config/robot.yaml`，再重新生成 USD 和 MJCF。

### 3.12 延迟测量
1. 固件里给每个环节打时间戳：
   - IMU 读到数据；
   - 电机反馈帧到达；
   - 推理开始和结束；
   - CAN 指令发出。
2. 记录 1 分钟，统计各段延迟的均值和最大值。
3. 用 §3.9 回放对比时，仿真和实车之间的时间差，减去固件内部的延迟，大致就是电机自身的响应延迟。
4. 结果写进 `config/robot.yaml` 的延迟部分，作为训练中延迟随机化的范围。

### 3.13 上车流程（第一次和以后每个新策略都按这个流程）
1. **板上检查：** golden vector 比对通过；打印推理耗时。
2. **观测检查：** 车放在架子上不使能电机，手动转每个关节、倾斜机身，用串口实时打印 35 维观测，逐项对照指南 §5.2 检查正负号、零点和顺序。
3. **架空运行：** 车吊起来，轮子离地，使能电机，运行策略，指令为 0。腿应该平稳停在默认姿态附近，没有抖动。再给小速度指令，看轮子转动方向是否正确。
4. **吊带落地：** 吊带稍微松一点，车着地，零指令站立 30 s。
5. **低速测试：** 前进和后退 0.3 m/s → 原地转向 → 调高 → 手推抗扰。
6. **每一项测试都录视频和 H7 日志。** 出问题时，把同一段指令放进 MuJoCo 回放，和日志对比。

**FW1 电机驱动和控制节拍改造**（影响公共模块，一定要保持其他机器人兼容）
- **DM 驱动**（`Modules/motor/DMmotor/`）：
  - 增加完整的 MIT 接口（p、v、Kp、Kd、τ），原来的纯力矩接口保留；
  - 增加失能和清错的 API。命令帧是 `FF×7` 加命令字节：0xFC 使能、0xFD 失能、0xFE 设零位、0xFB 清错（驱动 L28-32 已经有这几个定义）；
  - 修复 `DMMotorTaskInit` 里 `dm_task_name[5]` 被 strcat 反复追加导致的越界（L264-270）；
  - 离线回调里的 `osDelay(100)` 会阻塞 daemon 任务，改成非阻塞（L106-110）；
  - 检查反馈取反的逻辑（L91）；
  - 把 PMAX/VMAX/TMAX 改成按电机实例配置，wheel_leg_rl 使用 `gen_config.h` 里的值。
- **FDCAN 过滤器：** ioc 里每一路的 `StdFiltersNbr = 1`，但 `CANAddFilter` 会把索引递增，同一路总线挂多个设备时可能越界。把过滤器数量改大到不少于每路的设备数，再配置全局过滤器，拒收不匹配的帧。
- **统一控制节拍：** wheel_leg_rl 用一个 500 Hz 的控制任务（`vTaskDelayUntil` 或者 TIM 中断），在同一个周期里依次读状态、算 PD、发 4 个 DM 帧和 1 个 C620 帧。**不使用**现在每个 DM 电机各自 1 kHz 的任务，DJI 电机也纳入这个统一任务。INS 仍然 1 kHz 运行，控制任务读它的最新结果。
- **安全：** 你决定暂时不修改 VT13 模块，没问题，**但 wheel_leg_rl 应用必须自己判断遥控是否在线**：通过 daemon 查询遥控器的在线状态，离线时进入 SAFE_STOP。原因是现在 VT13 离线后旧指令会一直保持（`VT13.c:103` 被注释掉了），轮腿会按最后一个指令一直跑下去。
  - 另外增加统一的急停层：遥控离线、IMU 异常、关节越限、策略输出 NaN 或越界时，进入阻尼或失能。硬件急停开关（§3.0）始终保留。
- **验收：** 示波器或 DWT 时间戳显示控制周期 2 ms ± 50 µs；6 个电机的反馈都能收到；拔掉遥控器时 100 ms 内进入安全状态；其他机器人目标编译不受影响。

**FW2 二进制遥测**

**FW4 RL 推理运行时**（`Modules/rl_policy/`）

### 5.3 云端实例：第一次搭环境（约 2–3 小时，做完保存成镜像）
1. **租实例：** RTX 4090，**镜像选"IsaacSim5.1 + IsaacLab2.3.2 workstation 版"**（Ubuntu 24.04，CUDA 12.8），并**挂一块数据盘**（50–100 GB）。选这个镜像的理由：
   - **版本完全对得上：** SCUT 的环境是 Isaac Sim 5.1 + Isaac Lab 2.3.x，supermimic_wheelbipe 的 README 写的正好是 Isaac Sim 5.1 + Isaac Lab 2.3.2，PyTorch 2.7 + cu128 也一致 [码 SMW `docs/install.md`]。我们大量复用这两个仓库的代码，版本一致可以省掉很多兼容问题。
   - **不选 Isaac Sim 6.2 + Isaac Lab 3.0（CUDA 13）：** Isaac Lab 3.0 是大版本升级（supermimic_vibed 用的就是它，改成了 kit-less 方式，物理也可以选 Newton），SCUT 的代码没有在上面验证过，API 很可能对不上。等主线跑通以后再考虑升级。
   - **workstation 版和普通版都是 5.1 + 2.3.2：** 我理解 workstation 版带图形桌面（可以通过远程桌面打开 Isaac Sim 的界面），普通版只能命令行无头运行 [核：按平台说明确认]。你是新手，检查 USD 模型、看闭链和弹簧时有图形界面会方便很多，所以选 workstation 版；训练时照样用 `--headless`。如果两者价格不同而你又不需要界面，选普通版也可以。
2. **登录：** 用控制台给的 SSH 命令登录。在本机的 `C:\Users\Dai\.ssh\config` 里写一个 `Host gpufree` 别名（地址、端口、用户名照控制台填），以后 `ssh gpufree` 就能登录，scp 和端口转发也都用这个别名。
3. **在云端生成一个专用的 key，加到 Gitee 仓库的"部署公钥"（只读）：**
```bash
ssh-keygen -t ed25519 -f ~/.ssh/gitee_deploy -N ""
```
   然后把 `~/.ssh/gitee_deploy.pub` 的内容粘贴到 Gitee 仓库 → 管理 → 部署公钥。这样云端只能拉代码，不能推，即使实例泄露了也不会改坏仓库。
4. **找到数据盘的挂载路径**（在控制台看，或者执行 `df -h`），下文记为 `$DATA`。把它写进 `~/.bashrc`：
```bash
echo 'export DATA=/path/to/data_disk' >> ~/.bashrc
```
5. **拉代码：**
```bash
git clone --recurse-submodules git@gitee.com:<你的用户名>/wheelleg.git ~/wheelleg
```
6. **让训练输出写到数据盘：**
```bash
mkdir -p $DATA/runs && ln -s $DATA/runs ~/wheelleg/runs
```
7. **安装：** 按仓库 README（WP0 写好的）执行 `pip install -e` 安装各个包，并设置 pip 清华源。
8. **冒烟测试：** 跑一次 SCUT 的预训练权重 play（headless 加录像），确认能运行。
9. **在控制台保存自定义镜像**（如果平台支持），以后开新实例直接用这个镜像，不用再装一遍。

### 5.4 每次训练的固定流程
```
本机（或 Codex）改代码 → git commit → git push 到 Gitee
      ↓
云端开机 → cd ~/wheelleg && git pull && git submodule update
      ↓
tmux 里启动训练（输出写到 runs/，实际在数据盘上）
      ↓
本机用 SSH 隧道看 TensorBoard，隔一段时间看一次
      ↓
训练结束 → 云端运行评测和导出 → 把结果下载到本机
      ↓
云端关机（不训练时一定要关）
      ↓
本机：MuJoCo sim2sim → 填写 EXPERIMENTS.md → 决定下一步
```

**具体命令**（任务名和脚本参数以 WP4 写出来的 README 为准）：
1. 拉取最新代码：
```bash
cd ~/wheelleg && git pull && git submodule update --init --recursive
```
2. 开一个 tmux 会话（SSH 断开后训练也不会停）：
```bash
tmux new -s p1
```
3. 启动训练。**运行名称要有意义**，例如 `p1flat_e003_kp40`：
```bash
python isaac/scripts/train.py --task WheelLeg-P1-Flat-v0 --num_envs 4096 --headless --run_name p1flat_e003_kp40
```
4. 按 `Ctrl-b` 再按 `d` 离开 tmux。以后用 `tmux attach -t p1` 回来查看。
5. 云端启动 TensorBoard：
```bash
tensorboard --logdir ~/wheelleg/runs --port 6006
```
6. 本机另开一个终端做端口转发，然后在浏览器打开 `http://localhost:6006`：
```bash
ssh -L 6006:localhost:6006 gpufree
```
7. **从 checkpoint 续训**（改了奖励时用；改了观测或动作就必须从头训练）：rsl_rl 的 `--resume --load_run <运行名> --checkpoint <编号>` [核]。

### 5.5 训练过程中你要做的检查
| 时间点 | 看什么 | 怎么判断 |
|---|---|---|
| 开始后 5 分钟 | 终端有没有报错；FPS 是否正常 | 报错就停下来，把报错信息发给 Codex |
| 约 200 轮 | 回合长度是否在变长 | 一直很短，说明一开始就摔：停下检查模型和终止条件 |
| 约 1000 轮 | 各项奖励是否按预期变化 | 某一项惩罚过大：记下来，下一个实验再改 |
| 结束 | 评测表、play 视频 | 符合完成标准再导出；不符合就记进 EXPERIMENTS.md，设计下一次实验 |

### 5.6 下载结果、存档和实验记录
1. **云端导出：** 评测加导出（WP6 的脚本），会生成 `runs/<运行名>/export/`，里面有 `policy.onnx`、`policy_meta.yaml`、`golden.npz`、`eval.md`、`play.mp4`。
2. **下载到本机**（在本机执行）：
```bash
scp -r gpufree:~/wheelleg/runs/p1flat_e003_kp40/export D:/wheelleg_runs/p1flat_e003_kp40/
```
3. 同时下载**最后一个 checkpoint 和配置快照**（`model_xxxx.pt` 和 `params/`），以后要续训的话会用到。中间的 checkpoint 不用下载。
4. **在 EXPERIMENTS.md 里加一行：**

| 日期 | 运行名 | git commit | 改了什么（只写一处） | 轮数 / 时长 | 评测结果 | 结论 | 下一步 |
|---|---|---|---|---|---|---|---|

5. **决定发布的策略**（准备上车的），把 `export/` 里的 onnx、meta、golden 复制到 `config/policies/<策略名>_v<n>/`，提交进 git。
6. **定期清理云端数据盘：** 已经下载并记录的运行，删掉中间的 checkpoint，只保留最后一个。

### 5.7 控制费用

## 7. 出问题时怎么排查（新手版）

### 7.1 训练阶段
| 现象 | 最可能的原因 | 怎么查 |
|---|---|---|
| 一开始训练就报错 | 环境或依赖没装好；关节名和配置对不上 | 先跑一遍冒烟测试；把报错的最后 30 行发给 Codex |
| 机器人在仿真里一开始就倒、乱抖，甚至"爆炸" | 模型问题：闭链脱开、弹簧方向反了、质量或惯量错误 | 回到 WP4a，零动作静置测试 |
| 回合长度一直很短 | 终止条件太严，或者初始状态不合理 | 看每一项终止原因的统计 |
| 总奖励涨了，但 play 里动作很怪 | 策略在钻奖励的空子 | 逐项看奖励曲线，找出哪一项涨得异常 |
| 奖励先涨后突然下降 | 训练不稳定 | 回到下降前的 checkpoint，把学习率降低一半，或者把变化太大的奖励项权重降低 |
| 速度跟不上指令 | 指令范围超出机器人的能力，或者轮扭矩上限太低 | 缩小指令范围；检查轮扭矩和转速设置 |
| 零速时会溜车 | 延迟、零速奖励、观测里没有历史信息 | 指南 §7.2 的历史估计器 |

### 7.2 sim2sim 阶段
| 现象 | 最可能的原因 |
|---|---|
| MuJoCo 里一开始就倒 | 观测顺序或缩放和训练不一致；四元数顺序（wxyz 还是 xyzw）不同；轮子位置没有置 0 |
| MuJoCo 里走得动，但比 Isaac 差很多 | 两个仿真器的模型参数不一致（摩擦、armature、弹簧），先做开环对比 |
| 腿高频抖动 | PD 频率、延迟设置和训练不一致 |

### 7.3 上车阶段
| 现象 | 最可能的原因 |
|---|---|
| 一使能就倒 | 重力投影符号错；关节零点或方向错；观测顺序错 |
| 腿持续抖动 | 延迟比训练时大；Kd 不一致；电机 TMAX 没改，力矩被缩放了 |
| 能站但溜车 | 零速漂移问题；IMU 零偏没去掉 |
| 剧烈动作时腿突然软掉 | 电机欠压保护被触发（看反馈帧里的错误码 9） |
| 某个电机突然失能 | 通讯丢失超时（错误码 D）；CAN 总线负载或接线有问题 |

**通用排查方法**（华南虎的经验）：先查策略的输入和输出（观测有没有算错、缩放有没有对齐、动作限幅是否一致），再逐帧对比实车视频和仿真回放，找到差异出现的那一刻。

## 8. 推进节奏：辨识不省略，按最短路线并行推进

**原则（你定的）：**
1. **弹簧辨识、电机辨识（含扫频 real2sim）、延迟测量都严格做完，不为了进度省略。** 辨识和建模、固件开发同时进行，不等其中一个做完再做下一个，以此压缩时间。
2. **不用加宽随机化来代替辨识。** 随机化范围按指南 §5.7 的表格设定（SCUT 和星云在实车上验证过的范围），辨识结果用来设定标称参数，并检查这些范围能不能覆盖实车。
3. **跳跃是必须项**，目标是跳过隧道（指南 §6.6 的"跳隧道"部分），从第一周起就提前做可行性分析。

### 8.1 时间安排（约 5–6 周到实车平地，按 2–3 人估算 [判]）
| 周 | 仓库 A / 训练（你 + Codex） | 仓库 B / 固件（Codex） | 硬件和辨识（你） |
|---|---|---|---|
| 1 | 导出 URDF（云台作为一个刚体，通过 yaw 关节连接）；WP0；云端开机、保存镜像 | FW0、FW1（DM 驱动补全、500 Hz 统一控制任务、FDCAN 过滤器、应用层遥控离线保护） | §3.1–3.3 电机参数、C620、接线 |
| 2 | WP1 五连杆、WP2 USD 和模型验收、WP-ID 辨识脚本（先用仿真数据自测） | FW2 二进制遥测、FW3 扫频辨识应用 | §3.5 零点、§3.6 IMU、§3.7 称重 |
| 3 | WP3 MJCF 和 MuJoCo 环境（real2sim 回放要用）；WP4a/4b | FW3 实车联调 | **§3.8 力矩标定、§3.9 髋电机扫频 real2sim、§3.10 轮电机** |
| 4 | WP4c/4d；**辨识结果写回模型后**正式训练 P1-平地；**P3 可行性计算脚本**（指南 §6.6 第一步） | FW4 推理运行时 | **§3.11 气弹簧完整网格加阻尼、§3.12 延迟测量** → R5 |
| 5 | sim2sim（R7）；WP6 导出 | FW5 单策略应用；板上 golden vector（R8） | 准备上车的安全设施 |
| 6 | — | — | §3.13 上车：架空 → 吊带 → 平地（**R9**） |

**关键依赖：** P1-平地的**正式**训练要等 R5（辨识完成、参数写回模型）通过以后才开始。在这之前，只用 SCUT 的参数做冒烟训练，用来调试代码，结果不能拿去上车。

### 8.2 辨识的完成标准（达不到就不进入正式训练）
| 项 | 完成标准 |
|---|---|
| 力矩读数标定（§3.8） | 每个电机在 4 个姿态下的比例差异 < 5% |
| 髋电机 real2sim（§3.9） | 扫频 0.5–5 Hz、同相和反相、阶跃，仿真和实车的关节角曲线基本重合；**留出一组没参与拟合的数据做验证**，误差和拟合组相当 |
| 轮电机（§3.10） | 摩擦、阻尼、最大扭矩、空载转速都实测过；扭矩–电流曲线和 15.76:1 的估算对比过 |
| 气弹簧（§3.11） | 10×10 网格，有弹簧、无弹簧各一遍，两个方向；不同速度往返拟合出阻尼；左右弹簧分开；热机前后各测一次；两个电机算出的弹簧力一致 |
| 延迟（§3.12） | 各段延迟的均值和最大值；和 real2sim 拟合出的延迟一致 |
| 整车静态（§3.7、§3.11 第 7 步） | 3 个腿高下静止站立，实测电机力矩和仿真的差 < 10% |

### 8.3 辨识结果怎么用到训练里
1. **设定标称值：** 辨识得到的 armature、关节摩擦、阻尼、力矩缩放、弹簧的 F0/k/c（左右分开）、延迟、质量和质心，全部写进 `config/robot.yaml`，重新生成 USD 和 MJCF。
2. **随机化范围按指南 §5.7 设定，不因为进度而放宽。** 表里的范围已经在 SCUT 和星云的实车上验证过。
3. **用实测检查范围够不够：** 如果某一项的实际变化超出了表里的范围，就只把这一项扩大到能覆盖实测值。例如：
   - 左右弹簧的力相差超过 ±50 N；
   - 冷机和热机的弹簧力相差很大；
   - 实测延迟的最大值超出了表里的延迟范围。
4. **验证方法：** 把 §3.9 留出的那组扫频指令放进随机化后的 MuJoCo 里跑 50 次，实车曲线应该落在这 50 条曲线的范围之内。如果实车曲线落在范围外，说明标称值不对或者缺了某个效应，**回去补辨识，而不是加宽随机化**。

### 8.4 推迟到第一次上车之后的内容
只有这几项可以推迟，它们都不影响辨识和策略本身的正确性：
- 指南 §5.9 的按回报重置采样（第一版先用均匀采样）；
- 指南 §7.2 的历史估计器（先用单帧观测，实车出现零速漂移时再加）；
- 多策略切换（第一次只烧录一个策略）。

**不能推迟的：** 全部辨识、安全措施、零点和方向、IMU 的正负号、golden vector 比对、sim2sim。

### 8.5 第一次上车之后的技能顺序（RMUL、RMUC）
1. **P2 小陀螺**（第 7–8 周）。
2. **P1 加落地和台阶**（第 8–10 周）。落地预训练同时也是跳跃的基础。
3. **P3 跳跃（跳隧道，必须项）**（第 9–12 周，和第 2 项部分并行）：
   - 第 4 周起就要用可行性计算脚本，算出满力矩蹬伸能达到的跳高和行进跳距离；
   - 正式规则公布隧道尺寸后，立即对比能力和需求：够就进入训练；不够就提前改机构（弹簧、腿长、减速比），不要等到训练时才发现跳不过去；
   - 详细设计见指南 §6.6 的"跳隧道"部分。
4. **恢复控制器 R 和低姿态起身**（第 10–12 周）。
